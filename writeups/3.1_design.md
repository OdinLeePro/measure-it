## Decision and Model Suitability
Customers need immediate confirmation and a correct answer within an hour, not necessarily a decision made immediately. Support agents need a hold/escalation queue they can clear, with the rationale for *why* these tickets were queued attached. The Week 3 studio uses 50,000 tickets per month with a 10x peak, which I feel is a good scale for testing. Engineers own latency and cost budgets, whereas the support team owns the tradeoff between quality and automation.

The model receives ticket text and a summary of the user's account, then proposes an action, refund amount, and rationale:

| Path       | Decision                                   |
| :--------- | :----------------------------------------- |
| `answer`   | Information only                           |
| `refund`   | Up to \$50, no approval                    |
| `hold`     | Over \$50 through \$200, approval required |
| `escalate` | Over \$200, unclear, or uncertain          |

The model interprets ticket language / contents, but LLMs are inherently nondeterministic. Order lookups, arithmetic, refund caps, and approval checks may yield different results on repeated runs, and are therefore best left to code. Unclear / confusing cases should go to custom support staff, and safety should take priority over automation when review capacity is constrained.
